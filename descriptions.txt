PREFERENCE DATA STORE - COMPLETE TABLE DESCRIPTIONS
====================================================

SOURCE STAGING TABLES (External Data Ingestion)
================================================

STG_RELAY_CONSENT

Description: Landing table for consent updates from Relay Network for SMS servicing communications. Captures real-time API and daily SFTP feeds with client_id mapping to CFG products, phone numbers, and consent status (STOP/EXPRESS/WRITTEN).

Source: Relay Network via:
- Real-time API push events to Relay DTO API
- Daily SFTP batch process into DataLake (Integration done with OneTrust)

STG_ZETA_CONSENT

Description: Staging table for ZETA email and SMS marketing opt-out data. Contains LOB codes (0-30), email addresses, phone numbers, and respective opt-out statuses for marketing communications.

Source: ZETA vendor via:
- Daily SFTP process into DataLake
- Data sent to PDS database via ZETA Staging table using ZETA to OT Scheduler
- Integration done with OneTrust

STG_VINCIO_CONSENT

Description: Staging table for Vincio collections SMS consent updates. Receives daily feeds with account numbers and SMS consent status for collections communications.

Source: Vincio system via:
- Daily Oracle database feeds into DataLake
- Data received on daily basis into Oracle database (DataLake Schema setup is in progress)
- Cydne feeds collections SMS related consent updates into Vincio
- Integration pending with OneTrust

STG_GRYPHON_DNC

Description: Staging table for Gryphon National DNC (Do Not Call) Registry data. Contains phone numbers with DNC indicators and product family scope for telemarketing compliance per TCPA Guidelines.

Source: Gryphon National DNC Registry via:
- Monthly batch updates
- Integration pending with OneTrust
- Currently data is not being maintained in OneTrust but being used by Consumption interfaces as per legal approved business logic consent consumption

STG_OLB_ALERT

Description: Staging table for initial load of alert preferences from Online Banking (OLB) database. Contains UCID, account numbers, alert types, and configured metric values. Used only for initial migration.

Source: OLB (Online Banking) database via:
- Initial load only from OLB DB
- Once switchover is done to use PDS as SOR, APIs will be used to add/update/inactivate/delete alerts
- PDS will serve as the SOR for Alert Preferences


CORE CUSTOMER AND IDENTITY TABLES
==================================

DATA_SUBJECT

Description: Golden record for a person/entity whose preferences we manage. Stores the canonical data_subject_id, subject type, and crosswalk fields to map back to upstream customer identifiers (source_customer_ref_id, source_system_cd, master_data_subject_id). Uses UCID as the stable customer identifier.

Source: Master Customer / Party / CRM domain (customer MDM), plus batch/stream identity resolution jobs that link source IDs to the master subject.

ACCOUNT

Description: Represents the customer's account relationship(s) (e.g., checking, savings, loan) tied to the data subject. Enables preferences to optionally apply at the account level.

Source: Core banking / account servicing platform (usually batch from core + incremental updates from account events).

CONTACT_POINT

Description: Contact endpoints for the subject (email, phone, address, push token, etc.), with type and a primary_ind. Used for preference delivery channels and alert routing.

Source: CRM / customer profile service and/or communication platform (batch sync + near-real-time updates when customer updates contact info).


REFERENCE AND LOOKUP TABLES (Controlled Vocabularies)
======================================================

REF_SOURCE_SYSTEM

Description: Catalog of upstream systems that can send preference-related requests/events (RELAY, ZETA, VINCIO, GRYPHON, OLB). Used to validate and standardize "where data came from." Includes integration_type to classify REALTIME_API, DAILY_SFTP, MONTHLY_BATCH, etc.

Source: Enterprise integration governance / internal configuration (manually managed or CI/CD-managed reference data).

REF_LOB

Description: Line-of-business taxonomy (Retail, Cards, Mortgage, Wealth, etc.). Used to scope preferences by business domain. Maps to ZETA LOB codes (0-30) for marketing communications.

Source: Enterprise data governance / business taxonomy (manual reference data; slow-changing).

REF_CHANNEL

Description: Allowed channels for communication / delivery (EMAIL, SMS, PUSH, MAIL, IN_APP, etc.). Used to scope preferences and opt-outs by delivery channel.

Source: Communication governance / preference program config (manual reference data).

REF_PRODUCT_TYPE

Description: Product type taxonomy (LOAN, CREDIT_CARD, CHECKING, INVESTMENT, etc.). Lets preferences be scoped at a product-type level. Used for product-level consent and preference management.

Source: Product catalog / enterprise product master (reference feed).

REF_PRODUCT

Description: Specific product catalog entries (e.g., "Platinum Rewards Card", "Citizens Credit Card"), linked to product type. Used when preferences apply to a specific product. Maps to Relay client_id for product identification.

Source: Product catalog / product master (reference feed).

REF_EVENT_TYPE

Description: Event taxonomy for preference triggers and business actions (e.g., WITHDRAWAL, STATEMENT, FRAUD_ALERT, MARKETING_OFFER). Defines what events can trigger preference evaluation.

Source: Event governance / product analytics taxonomy (manual reference data; updated as new events are introduced).

REF_PREFERENCE_CATEGORY

Description: High-level grouping of preferences (e.g., NOTIFICATIONS, MARKETING, SECURITY, SERVICE). Provides top-level organization for preference types.

Source: Preference program configuration (manual reference data).

REF_PREFERENCE_TYPE

Description: Specific preference types within a category (e.g., "Low Balance Alerts", "Marketing SMS", "Paperless Statements"). Defines granular preference options available to customers.

Source: Preference program configuration (manual reference data).

REF_CONSENT_TYPE

Description: The level/type of consent (e.g., EXPLICIT, IMPLIED, REQUIRED_BY_REG, etc.) used to interpret consent_status_cd. Maps to Relay consent types (STOP/EXPRESS/WRITTEN) and TCPA compliance requirements.

Source: Compliance / legal-approved consent taxonomy (manual reference data).

REF_CONSENT_STATUS

Description: Current state of consent (GRANTED, DENIED, UNKNOWN, PENDING). Used to evaluate whether customer has given consent for specific communications.

Source: Preference program configuration (manual reference data).

REF_OPT_OUT_TYPE

Description: Types of opt-out mechanisms (GLOBAL_OPT_OUT, CHANNEL_OPT_OUT, CAMPAIGN_OPT_OUT, etc.) used to interpret opt_out_status_cd. Supports multi-level opt-out hierarchy.

Source: Compliance / communications governance (manual reference data).

REF_OPT_OUT_STATUS

Description: Current opt-out state (OPTED_OUT, NOT_OPTED_OUT, UNKNOWN). Used to enforce customer opt-out preferences across channels and campaigns.

Source: Preference program configuration (manual reference data).


SOURCE EVENT REGISTRATION AND AUDITING
=======================================

SOURCE_EVENT

Description: Registry of expected/valid source events coming from each upstream system (RELAY, ZETA, VINCIO, GRYPHON, OLB), optionally scoped by product/product_type/event/preference_type/category/LOB/consent/opt_out, plus priority_nbr. This supports validating inbound requests ("are we expecting this source_event?") and routing by priority for conflict resolution. Critical for API validation and ensuring only registered source+product+event combinations are accepted.

Source: Integration onboarding/config maintained by platform team (initially manual; later could be managed through an admin UI or config-as-code).

SOURCE_EVENT_HISTORY

Description: Change history for SOURCE_EVENT entries (audit trail of config changes over time, who changed what, and why). Captures before/after snapshots in JSON format. Useful for troubleshooting integration issues and compliance audits.

Source: Internal system-generated whenever SOURCE_EVENT is created/updated/deactivated (application audit).


TRANSACTION AND REQUEST LOGGING
================================

CONSENT_REQUEST

Description: Operational request records tracking all inbound preference/consent requests from source systems. Includes request_type (CREATE/UPDATE/DELETE), channel_type (API/BATCH/STREAM), transaction_type, and links to source_event for validation. Provides real-time tracking of API calls and batch job execution.

Source: Preference API / Preference service (real-time API requests) + batch integration processes (SFTP/Oracle feeds) + stream processing jobs.

TRANSACTION_PAYLOAD

Description: Raw request/response payloads for consent requests. Stores complete JSON/XML payloads from source systems for debugging, replay, and compliance. Links to CONSENT_REQUEST for full transaction context.

Source: Internal system-generated on every API call or batch transaction processed by the Preference service.


CENTRAL PREFERENCE DATA MANAGEMENT (Current + History)
=======================================================

PREFERENCE_STATE_CURRENT ✅ Central system-of-record ("golden preference state")

Description: The centralized current-state preference table. One row represents the current preference status/value for a subject, scoped by the combination of dimensions (data_subject + channel + event_type + preference_type/category + consent/opt_out status + optional product/product_type/account/LOB + source_event), with priority_nbr to resolve conflicts. This is the table all downstream systems query to determine "what is the customer's current preference right now?" Single API upserts preferences into this grand table.

Source: Preference API / Preference service as the system of record. Populated from:
- Inbound preference create/update API calls (real-time)
- Inbound source events validated via SOURCE_EVENT
- Staging table ETL processes (STG_RELAY, STG_ZETA, STG_VINCIO, STG_GRYPHON, STG_OLB)
- Batch reconciliation jobs (optional) to correct drift

PREFERENCE_STATE_HISTORY

Description: Append-only history of changes to preference state (who/when/why), storing before/after snapshots in JSON format. Every state change retains source_event_id for provenance tracking. Used for traceability, dispute resolution, compliance audits, and regulatory reporting.

Source: Internal system-generated on every insert/update to PREFERENCE_STATE_CURRENT (database trigger or application-level audit).


ALERTS AND METRICS (Preference-Driven)
=======================================

PREFERENCE_ALERT_REFERENCE

Description: Catalog of alert definitions that can be enabled for customers (e.g., "Low Balance Alert", "Large Withdrawal Alert", "CD Maturity Notice"). Used as the master list for alert linking. Contains 12 alert types as per OLB confluence page data.

Source: Alert product configuration / notification platform configuration (manual/reference feed) + initial load from OLB database.

PREFERENCE_ALERT_METRIC_REFERENCE

Description: Catalog of metrics/parameters that an alert may require (e.g., threshold_amount, rolling_window_minutes, check_number, frequency), optionally linked to a reference data type. Defines what "tunable knobs" exist for each alert. Supports both Category A (account-level setups) and Category C (customer-level setups) from OLB.

Source: Alert product configuration / rules engine config (manual/reference feed) + OLB alert metric definitions.

PREFERENCE_REF_DATA_TYPE

Description: Generic reference type/value table to define metric data types and allowed values (e.g., ENUM sets, units, formats). Supports validation/UI dropdowns for alert configuration.

Source: Platform configuration / governance (manual reference data).

PREFERENCE_CUSTOMER_ALERT_LINK

Description: Customer-level enablement of an alert (which data_subject/account/contact_point is subscribed to which alert), including activation/inactivation timestamps. This is the "customer subscribed to alert X" bridge table. Maps to OLB's alert configurations with UCID, account numbers, and contact values. For one alert setup (e.g., Low Balance), can create up to 5 records in PDS if alert is set up for UCID + 3 accounts + 2 contact values.

Source: Preference API / Alert subscription API (real-time user changes) + batch loads from legacy OLB alert platforms during migration (initial load only; post-switchover uses PDS as SOR).

PREFERENCE_CUSTOMER_ALERT_METRIC_LINK

Description: Stores the configured metric values for a customer's alert subscription (e.g., for "Low Balance Alert", threshold_amount = 100.00, for "Transaction Cleared", exact_amount = 100.00, transaction_type = "any debit"). Ties to customer_alert_link and alert_metric_reference. Maps OLB alert metrics like ia_subcode, ia_accttype, check_number, etc.

Source: Preference API / Alert subscription API (real-time) + batch migration from legacy OLB alert systems (initial load with metric configurations).


DATA FLOW SUMMARY
=================

External Sources → Staging Tables → Validation (SOURCE_EVENT) → Request Logging (CONSENT_REQUEST) → Central Store (PREFERENCE_STATE_CURRENT) → History (PREFERENCE_STATE_HISTORY)

RELAY (Real-time API + Daily SFTP)
  → STG_RELAY_CONSENT
  
ZETA (Daily SFTP)
  → STG_ZETA_CONSENT
  
VINCIO (Daily Oracle)
  → STG_VINCIO_CONSENT
  
GRYPHON (Monthly Batch)
  → STG_GRYPHON_DNC
  
OLB (Initial Load Only)
  → STG_OLB_ALERT

All staging tables processed by:
  → SOURCE_EVENT validation (priority-based)
  → CONSENT_REQUEST logging
  → PREFERENCE_STATE_CURRENT (golden record)
  → PREFERENCE_STATE_HISTORY (audit trail with source_event_id)

Downstream consumers query PREFERENCE_STATE_CURRENT for current preference state.
